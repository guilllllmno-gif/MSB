# 风控原型（rc-app）· MSB 全业务风控仪表盘 + 交易监控流水线 + 关联团伙

> 给下次接手 / 新会话快速续接用。代码在 `rc-app/`，分支 `msb-lifecycle-state-transition`。
> 业务背景：加密货币型 MSB（FuturePay CA，CAD / FINTRAC 口径）。业务线：On-ramp（法币买币）、Off-ramp（卖币出金）、虚拟货币兑换（币币）、充值、提现。

## 一、技术与视觉
- React + `@heroui/react` v2 + Tailwind v4 + Vite。路由级代码分割（`React.lazy`）。
- 字体：Golos Text（全局 `--font-sans`）。**所有英文统一用 Golos Text，不使用 `font-mono`**（地址 / 哈希 / ID 也用）。
- 布局：灰色侧边栏（可收起）+ **白色内容区（无圆角包裹、无滚动条）**；深色模式用 HeroUI 原生主题。
- 圆角层级：容器 16（`.card`）/ 控件 12 / 小标签 8 / 徽章 6 / 胶囊 full。
- 详情页顶部为**扁平页头**（不用卡片框包）。共享 `components/Timeline.tsx`（HeroUI 无 Timeline，自建）。
- 配色克制：蓝（brand）+ 灰为主。**核心口径:只有「状态」可用色徽标 —— 生命周期/工作流状态(已上线/待复核/调查中/已报送…)用色;类别/类型/执行场景/风险等级/上线策略/适用对象/关联类型等「属性·取值」一律中性灰**(取值是设置值、不是状态)。避免一行里多种彩色徽标堆叠的「花花绿绿」。已落地:监控规则列表 / 规则详情(venue·风险等级·上线策略徽标转灰)、名单管理 / 名单详情(类别·类型·关联类型转灰),状态徽标保留色。表内单列的「结果/状态」单元格(处置结果·命中动作)可保留色。`Pill` 默认 `tone="grey"`。**主体/商户头像统一中性灰**(`Initials` 加 `mono` prop —— 头像不承载状态,一排彩色圆点纯属噪声):已应用于团伙列表/详情的成员头像(图谱节点 / 连线端点 / 成员卡),分析师(经手人)头像仍保留个人色作身份区分。**全站扫一遍已落地**:团伙(列表/详情/新建抽屉)、告警详情的关联团伙成员、主体档案 360(目录行 / 档案头像 / 关联主体)的商户头像 → mono 灰;`Initials` 调用方加 `mono`。**检测维度 `FDIM` 配色 → 中性灰**(事后监控列表 / 事后详情 / 案件详情的维度徽标,图标+标签仍区分维度)。**团伙页**进一步收敛:洗钱手法徽标(原按 risk 上色)、共享维度 chips(原 资金/地址/设备/IP 四色)、成员类型徽标 → 中性灰,**只留 置信度% + 状态 + 图谱连线维度色** 作视觉重点(图谱连线 / 置信度构成堆叠条的维度配色是分析核心,保留)。
- 提交后自动 commit + push 到 origin（见全局记忆 auto-push）。每次实质改动同步更新本文档（见记忆 update-rc-doc）。

## 二、风控仪表盘（`pages/Dashboard.tsx`，`/dashboard`，默认首页）
**MSB 全业务线风险总览**，不是单一业务看板。自上而下：
- **角色视角切换（演示态，核心）**：同一仪表盘按**当前是谁**换内容 —— 页头胶囊切 **一线分析师（James Liu）↔ 风控总管·兼MLRO（Emma Zhang）**，下方**职责分工条**（左色条 + 头像 + 角色徽标）说明该角色能做什么。两视角差异：① **需立即处理 banner** —— 分析师版为团队态势全量（超SLA / 报送 / 待认领案件 / 待认领团伙）；总管版只留「团队超SLA·需介入」（报送已并入「待我审批」、待认领已并入「团队负荷」，不重复）。② **个人队列 ↔ 团队负荷** —— 分析师显「待我处理」（个人队列）；总管显「团队负荷」（`AnalystLoad` 全员柱 + 超载人数 / 待派单计数，点柱下钻改派，见二·补）。③ **风险评分分布** —— 分析师只读（阈值由总管在全局策略调）；总管 `editable` 双滑块可拖，实时重算三区占比 + 直通率 + 较基线（40）增量（`countBelow` 跨桶按比例插值）。④ **待我审批卡** —— 总管专属（分析师不可见），见下。`role` state 切换，`ME`/`HEAD` 两身份。
- **待我审批（总管专属）**：只有风控总管能拍板的**四类决策**汇成一张审批收件箱，全部从真实 store 派生、与各自列表页同口径 —— **规则上线**（`RULES` state=pending，带回测误报 + 提交人）/ **规则变更**（已上线规则的拟议变更，`ruleStore.allPending()`，带字段 diff 摘要 + 提交人）/ **案件升级**（case state=mlro）/ **报送签发**（report `liveStatus`=review）/ **名单复核**（list status=pending），每项深链到对应详情页（规则两类落到规则详情顶部横幅审批，见六节「变更治理」）。分析师视角此卡隐藏。
- **风控流水线总览**（`components/PipelineMap.tsx`，置于仪表盘最顶）：给第一次用的人一张「一笔交易怎么流动」的地图 —— **主链** 事中监控 →(转研判)→ 告警研判 →(升级/建案)→ 案件管理 →(起草STR)→ 报告报送 →(结案)→ 处置记录;**旁路汇入** 事后监控 / 关联团伙 → 直连研判·案件;**反馈闭环** 事后规则回填 → 监控规则 → 回到事中拦截。每个节点带在办计数、可点进入。解决"模块都在但新人串不起来"的问题。
- **需立即处理** banner（团队级）：SLA 超时 / FINTRAC 报送临期 / 冻结资金 / 待认领团伙。**系统自动推送、按时限排序，不需人工设优先级**（时钟 / 法定倒计时 / 制裁命中等客观信号驱动）。
- **业务线风控总览**（头条）：5 条业务线一张表（资金流向 / 今日笔数 / 金额 / 告警 / 直通率 / 关键风险），风险点小圆点上色。
- **风险防御 / 业务转化** 双指标面板（14 日趋势折线）—— 风控的双重价值：拦下风险 + 让合规交易放得更多更快。
- **待我处理 + 风险评分分布**（同一行）：待我处理是**个人队列**（从 `ringStore` 拉自己拥有的团伙 + 静态告警 / 报送 / 案件待办）；评分分布是 Stripe Radar 式直方图（阈值分 放行 / 人工 / 拦截 区）。
- **告警队列健康度**（运营脉搏 · 摘要卡）：整张卡可点,跳运营总览（`/ops`）。顶部**状态判定胶囊**（健康 / 偏紧 / 超负荷）+ 一行 5 格体征（待处理积压 / SLA 达成率 / MTTR / 超 SLA 件 / 团队负荷 `超载人数/总数`），数据由 `lib/opsMetrics.ts` 的 `queueHealth()` 派生 —— 与运营总览页同源,判定口径一致。完整图表（燃尽 / 停留 / 分析师负载）下沉到运营总览,仪表盘只留一眼可读的健康摘要。
- **交易处置漏斗**（业务无关）：发起 → 制裁/名单筛查 → 规则评分 → 自动放行，全业务线统一闸口。
- 收入提升机会 / Top 命中规则 / 关联团伙概览 / 高风险交易信号 / 链网络分布。
- **图表交互**：共享 `LineChart`（与 `AnalystLoad`、`DAYS14` 一并抽到 `components/charts.tsx`，供仪表盘 + 运营总览复用）自带 hover tooltip（竖向辅助线 + 各序列圆点 + 数值浮窗，用百分比定位不受 SVG 拉伸影响，支持 `labels`/`valueFmt`/`name`）；donut / 柱 / 直方图 / 网络条用原生 `<title>`；`AnalystLoad` 柱有同款浮窗。
- **可读性**：去行话、用日常词（产能→正常上限、在办→手头任务、超载→忙不过来、转化率口径标清），**每张图配一行大白话注脚**说明怎么读。
- **跨模块数据自洽（关键）** —— 仪表盘里凡是「能在别的页面点开核对」的数字都**从各 store 真实派生**，与列表页同口径，不再硬编码假数：① **需立即处理 banner** —— `告警超 SLA`（调查车道 + sla 红，同 AlertList）/ `FINTRAC 报送待处理`（review + returned，同 ReportFiling 需立即处理）/ `案件待认领`（active 且未分配，同 CaseList 显「认领」的件）/ `待认领团伙`（ringStore pending）；**零计数的 chip 自动隐去**，全清空时 banner 转绿显「已全部清空」。② **待我处理（个人队列）** —— 不再用不存在的假 ID（原 ALT-2418 / CASE-2026-014 等死链），改从**真实记录**派生：归我或未分配（待认领）的 告警（非 closed）/ active 案件 / 我起草的 active 报告 + 我拥有的团伙，**每项深链到真实详情页**（`/alert?id=` `/case?id=` `/report?id=` `/ring?id=`），超时项排前。③ **Top 命中规则** —— 取自 `lib/rules.ts` 真实 live 规则按 `hits30` 降序前 4（行可点进 `/rule?id=`），误报率 ≥20% 标红，注脚指向真实最高误报规则（新商户首充 26%）；去掉原 mock「误伤金额」列。④ 关联团伙概览（待认领/调查中/高置信 + Top3）本就 live。订阅 `useAlertVersion/useCaseVersion/useReportVersion/useRingVersion`，处置后实时联动。（业务线表 / 双指标趋势 / 评分分布 / 队列健康度等聚合「今日」量级数仍为设计态 mock，与样本列表不同尺度、不构成矛盾。）

## 三、交易监控流水线（核心模型）
一笔命中规则的交易，按生命周期在四个页面间**串行流转**，**任一时刻只属于一个页面**。

### 车道模型（按 `state` 区分，定义在 `lib/data.ts`）
- `GATE_STATES = [new, pending]` → **事中监控**（实时闸口车道）。
- `INVESTIGATION_STATES = [progress, pending_l2, escalated]` → **告警研判**（调查车道）。
- `closed_*` → **处置记录**（归档）。
- 状态机仍是 `RC_STATES`；状态 / 经手人 / 事件存 `alertStore`（内存，刷新重置，无后端）。

### 先后顺序
- **实时交易命中规则** → 先进 **事中监控**；当场拍不了板 →「转研判」→ 进 **告警研判**。
- **事后 / 批量 / 团伙检测** → **直连告警研判**（无事中环节，钱已动）。
- 不是每笔都会进告警研判：事中能当场放行 / 拒绝的，直接进处置记录。

### 四个页面
- **事中监控**（`pages/Monitoring.tsx`，`/monitoring`）：回答「这笔钱放不放」。实时指标条 + 充值 / 提现 Tabs + 告警样式表格（按 SLA 紧迫度排序）。行操作 = 查看(进详情) / **审核(行内开 `ReviewDialog` 抽屉)** —— **三个监控列表(事中 / 事后 / 告警研判)统一为行内抽屉审核**。
- **告警研判**（`pages/AlertList.tsx` + `AlertDetail.tsx`，`/alerts`，**原「交易警报」改名**）：回答「这单可疑吗、要不要转合规上报 STR」。只显示调查车道；tiles = 调查中 / 待 L2 复核 / 已升级；每行 **来源徽标**（实时升级 = 事中转研判 / 事后检测 = 回溯直连）。**事中 / 告警详情(`AlertDetail`,info tab,两车道共用)带「关联线索·跨模块」卡**:除已有的关联团伙(`ringsForMerchant`)外,自动按主体匹配**同主体的事后命中 + 案件**(可跳转),提示升级 / 转研判 / 建案时并入同一案件,避免重复立案 / 重复 STR —— 让关联视图在四个监控页(事中 / 事后 / 告警 / 案件)全覆盖。
- **事后监控**（`pages/PostMonitoring.tsx`，`/post-monitoring`）：交易完成后的回溯 / 批量检测（结构化拆分、扇入归集、休眠突发、币币链跳、速度骤增、对手集中度）。两层状态：
  - **批次状态**（轻量）：扫描汇总卡上显示 `批次号 + 已完成 + 完成时间 + 下次计划`，不做成重表（分析师关心命中项,不关心批次）。
  - **命中项状态机**（分析师天天碰的主体，似告警但有事后特有项）：`新建·待认领 →(认领)→ 处理中 →(补料 RFI / 升级 L2·MLRO)→` 终态。终态比事中多两种：**已结·确认可疑·转报送**（补 STR）、**已结·转案件**，外加 **已结·误报**。状态 tiles + 状态列 + 按状态门控操作；终态处置走**处置弹窗**。
  - **事后特有两维度**：**⑧ 已出账·需追溯** —— 资金已不可逆流出（事中还能冻结，事后不能），确认可疑时必填**资金追溯评估**（可追溯·冻结下游 / 部分 / 不可追溯·上报损失），并打「已出账·需追溯」标记；**⑨ 规则回填** —— 结案时可把该 typology 回填检测规则（默认勾选），让事中即时拦同类（事后 → 规则优化闭环，事中没有这条）。
  - **审核：列表内联 + 详情页两条路径**（与告警研判一致）。列表（`PostMonitoring.tsx`，含 SLA剩余 / 分配给 列）行操作**按状态自适应**：`新建·待认领`→「认领」（直接认领）、其余 active 状态→「审核」（**列表内联打开 `FindingReviewDialog` 抽屉**，无需先进详情）、终态→仅「查看」。眼睛图标始终进 **`pages/PostDetail.tsx`（`/finding?id=`）** 看完整研判工作台（详情页顶部也有同一个「认领 / 审核」入口）。**处理中 → 确认可疑 → 追溯中** 即在该抽屉内完成。命中数据 `lib/findings.ts`，状态 / owner / 追溯 / 冻结 / 损失 / 回填 / 事件存 `findingStore`（`lib/store.ts`，内存，跨列表↔详情持久）。
  - **审核走右侧抽屉**（与告警研判一致）：详情页顶部 `new` 状态显「认领」、其余 active 状态显「审核」按钮 → 打开 **`components/FindingReviewDialog.tsx`**（右侧抽屉，样式 / 宽度同 `ReviewDialog`）。抽屉按命中状态自适应：**处置结论**（确认可疑 / 转报送 / 转案件 / 误报关闭）+ **流程操作**（补料 / 材料已回 / 升级）选择卡 + 操作后影响 + 调查依据；**终态结论(转报送 / 转案件 / 误报关闭)必填结构化「处置理由」**（`FREASONS`，记审计日志，与告警 `ReviewDialog` 一致）；选「确认可疑」时展开资金追溯评估（必填）+ 规则回填勾选。**资金追溯三档联动追回组处置**（`TRACE_TIERS` / `traceRecovery`，`lib/findings.ts`）：选档位给「追回组」一个**默认建议**(**可追溯·已冻结→默认请求下游冻结**;**不可追溯→默认上报已发生损失**;**部分可追溯→不预设**)。**默认建议不互斥、不禁止**——只「加」对应默认动作、不清除另一项,冻结与损失可并存(如可追溯但部分已流失),另一项仍可在追溯工作台手动补登;**止损组(封号 / 列名单 / 规则回填)保持手动**。**详情页顶部不再有一排内联动作按钮**；`追溯中` 状态顶部显 **「追溯处置」(主)+「结案审核」(次)** 两个按钮:追溯处置开 **`components/TraceDrawer.tsx`** 右侧抽屉(同款样式),结案审核开 `FindingReviewDialog`(转报送 / 转案件)。

## 八、主体档案 · 360（`pages/EntityProfile.tsx`，`/entity`）
**跨模块商户360**。**主体 = 商户(法律实体)单一维度**(刻意决定):MSB 的 KYC 锚点、可问责对象(限额/冻结/STR/停业)都是商户;**地址 = 商户名下属性**(见下「关联链上地址」)、**行为 = 归属记录**,均不另作主体——避免同一坏人被摊成几十个地址档案。无归属的外部地址(混币器/制裁钱包/对手交易所)归 **名单管理** 或 **案件子主体**,不进主体档案。把商户在 **事中 · 事后 · 告警 · 团伙 · 案件 · 报送** 的全部足迹聚到一张视图,解决「同商户被各模块割裂、各开一案、重复 STR」。聚合逻辑 `lib/entity360.ts`(纯派生,只读静态数据;页面用各 store version hook 叠加实时状态)。
- **归一化匹配器**（核心）：同一主体在各模块名字写法不一（告警 `NovaPay Technologies Ltd.` / 事后·团伙 `NovaPay Technologies` / 报告 `OffshoreFX Ltd. · 0x7F4a…9c21`）。`entityKeys(name)` 把名字拆成可匹配「身份键」数组：**链上地址**（`0x…` / base58 截断）→ 地址键；**团伙号** `RING-xxxx-xxx`、**设备群** `#A7` → 各自键；**商户** → 去标点 + 去公司后缀噪声词（ltd/inc/corp/technologies/exchange/systems…）取核心 1-2 词。`sameEntity(a,b)` = 两名字任一键重合。一个报告主体含「商户 + 地址」两键，故两边都能命中。

## 九·补、全局策略 · 系统兜底（`pages/StrategyPage.tsx`，`/strategy`）
风控的**安全网底座**:在逐条「监控规则」(显式拦截逻辑) 与「名单」(筛查数据) 之外,系统**始终生效的全局默认与兜底**——回答「没规则命中怎么办 / 规则·名单冲突听谁的 / 数据缺失或系统降级时如何保守处置」。三层配置 = 逻辑(规则) + 数据(名单) + 兜底(本页)。
- **三原则**:**默认从严 fail-safe**(无命中 / 评分缺失·超时 → 默认更保守档,不默认放行)/ **最严生效 most-restrictive**(多命中取最严动作)/ **法定不可豁免**(制裁·LVCTR·STR·留痕始终生效)。
- **① 决策基线·风险分处置矩阵**:无规则命中时按综合风险分分诊 —— ≥80 拦截+人工 / 60-79 放行+转研判 / 40-59 放行+留痕 / <40 直接放行;**评分缺失·超时默认按「偏高·转研判」**(从严)、大额暂缓。**呈现改版**:原三列表格换成 **0–100 渐变分段条**(四档按区间跨度着色 `<40` 占 40%、其余各 20%,低→高 左→右,下方 0/40/60/80/100 刻度)+ 下方四张**档位卡**(区间 / 动作 / 说明,卡头一颗小色点标严重度,正文中性)。**借鉴 Stripe Radar「Risk controls」**:段条上方加一张**「当前处置基线」突出卡**(盾/表盘图标 + 当前预设档徽标 + 一句话当前阈值「≥{block} 拦截+强制人工 · {review}–{block-1} 转研判 · <{log} 放行」+ 右侧「调整基线」按钮,呼应 Stripe「Currently blocking payments with a risk score of 75 and higher / Select risk setting」)。
  - **调整基线操作(真交互,非占位)**:处置基线 = 三个风险分切点 `Thresholds{block/review/log}`(默认 80/60/40),四档区间由 `makeBands` 派生、段条宽度按切点跨度算。点「调整基线」开 **预设档弹窗**(对标 Stripe「Select risk setting」):三档 `BASELINE_PRESETS` —— **保守·更早拦截**(70/50/30)/ **标准·平衡(推荐)**(80/60/40)/ **宽松·减少打扰**(90/70/50),每档卡内单选 + 切点预览 chips(≥block 拦截 / 转研判 / 留痕 / 放行)。选档「提交双人复核」即 `setThresh` —— **段条 / 档位卡 / 当前基线卡文案实时联动**(本地 state 演示,toast 提示已提交双人复核 + 记审计;接后端落 `policyStore`)。未改档时提交按钮禁用。法定硬约束(制裁 / LVCTR / STR)不受基线影响,弹窗内注明。
- **② 法定硬约束(锁定·只读)**:制裁筛查(命中即冻结+TPR,白名单不可豁免)/ LVCTR ≥CAD 10,000 自动报送 / STR 30 日时限 / 记录保留 ≥5 年。
- **③ 冲突仲裁·优先级**:最严生效;名单 制裁>黑>关注>白(白名单仅豁免评分类、不豁免制裁/黑);层级 法定>名单>模型>规则>基线。
- **④ 准入与默认限额**:未完成 KYB 默认禁提现+限额 / 新商户首充观察期 / 按 KYC 分级三档限额 / 高风险辖区加严 EDD。
- **⑤ 数据缺失·系统降级兜底(核心)**:链上溯源失败→转人工暂缓 / 制裁名单源不可达→fail-closed 暂停放行(锁定) / 评分服务故障→**熔断·全局保守模式** / KYC 缺失→按最高风险档 / 通道拥塞→低额优先余者排队。
- **⑥ SLA 超时兜底**:告警超时→自动暂缓冻结(防超时即放行) / 案件超时→升级 MLRO / STR 临期<5天→加急 / 名单到期未复核→维持生效(从严)。
- **⑦ 变更治理**:可调项双人复核(MLRO+风控负责人)+ 全量审计 + 灰度回测;法定项只读。
